# Model Compression and Quantization

Patterns for compressing AI models for deployment on resource-constrained embedded hardware.
Compression reduces flash/RAM footprint for flash-constrained targets. Compression
requirements differ by technique:

- **Quantization (`dlquantizer`):** requires a **native dlnetwork** with built-in layers —
  imported networks with custom autogenerated layers are not supported.
- **Projection (`compressNetworkUsingProjection`):** works on imported networks **as long
  as the learnables live in built-in layers** (e.g., `fullyConnectedLayer`, `lstmLayer`,
  `convolution2dLayer`). The more common blocker is **unformatted dlarray inputs**:
  imported networks frequently end up with input formats labelled `"UU"` or `"UUU"`,
  which the projection PCA step cannot interpret. Workarounds typically involve wrapping the
  imported network so the input is presented with a proper format (`"CB"`, `"CBT"`,
  `"SSCB"`, etc.) before calibration.
- **Pruning (`compressNetworkUsingTaylorPruning`):** also expects a native dlnetwork.

For maximum compatibility, rebuilding as a native dlnetwork remains the safest path.

**Choose the compression path before applying techniques.** The right combination of
pruning, projection, and quantization depends on the user's hardware target, deployment
goal (flash vs SRAM vs latency vs accuracy), and retraining tolerance. Load
[`compression-decision.md`](compression-decision.md) at the start of Phase 5 and walk
the user through the question flow before applying any technique. Compression is not
mandatory and is not always optimal — for example, on ARM Cortex-M with a latency-bound
LSTM model, the float32 path with CMSIS-DSP matrix-multiply replacement outperforms a
quantized path because CMSIS-NN provides no INT8 kernels for recurrent layers.

## Compression Techniques Overview

The table below summarizes the **mechanism** of each technique. **Flash, SRAM, and
accuracy outcomes are model-dependent** — especially for structural compression
(pruning and projection), where the same reduction goal can produce very different
results across architectures and datasets. Always measure on the actual model with
held-out data before committing to a path.

| Technique | Function | Flash impact | SRAM (activation memory) impact | Accuracy impact | Retraining |
|-----------|----------|--------------|-------------------------------|-----------------|------------|
| **Pruning** (structural) | `compressNetworkUsingTaylorPruning` | Reduces — removes filters, so weight matrices shrink | **Reduces** — fewer activations to store between layers | Model-dependent; iterative scoring + fine-tuning aims to hold accuracy within the user's budget | Required (between iterations) |
| **Projection** (structural) | `compressNetworkUsingProjection` | Reduces — low-rank factorization shrinks weight matrices | Does **not** reduce | Model-dependent; do a trade-off analysis | Typically required; modest goals can be tried without retraining as a trade-off pass |
| **INT8 quantization** (non-structural) | `dlquantizer` (`prepareNetwork`, `calibrate`, `quantize`) | Up to ~4× from the FP32 → INT8 weight storage drop, before per-layer overhead | Activation buffers also drop to INT8 (up to ~4× depending on shapes) | Model-dependent; usually small for CNN/FC, depends on output dynamic range and calibration set | Not required (post-training) |
| **Combined** (pruning and/or projection + quantization) | All of the above, in order | Multiplicative across techniques | Multiplicative (skip projection if SRAM is the goal) | Model-dependent; ~77% combined flash savings has been reported on representative CNN + FC examples | Required for the structural stages |

A separate manual INT8 (per-matrix min-max scaling) fallback is documented in
[`compression-quantization.md`](compression-quantization.md) for cases where
`dlquantizer` is not viable; it is a storage-only optimization that does not produce
integer arithmetic in generated code.

**No single recommended default.** Pick the technique based on the goal collected via
[`compression-decision.md`](compression-decision.md):

- **Flash-bound + retraining OK** → combined **pruning + projection + quantization**
  (each technique attacks a different source of flash; combining them is multiplicative)
- **Flash-bound + no retraining** → quantization, optionally with a conservative
  projection trade-off pass on overparameterized models (try the default
  `ExplainedVarianceGoal=0.95` first, or sweep `LearnablesReductionGoal` and
  measure accuracy)
- **SRAM-bound** → **pruning + quantization** (skip projection — it does not reduce
  activation memory)
- **Latency-bound** → hardware-dependent. Structural compression (pruning, projection)
  is also worth trying — fewer MACs typically means lower latency, and on MCU targets
  the structural savings can dominate kernel-replacement gains. On Cortex-M with
  recurrent layers, skip quantization for the LSTM/GRU portion (CMSIS-NN has no
  INT8 recurrent kernels; float32 + CMSIS-DSP is faster).
- **Accuracy-first** → try compression with accuracy gating before falling back to
  the float32 baseline. `compressNetworkUsingTaylorPruning` exposes a
  `ValidationThreshold` NVP that stops pruning as soon as the validation metric
  drops below the threshold; quantization with proper calibration often preserves
  accuracy on overparameterized models.

## Compression Order (Combined Pipeline)

For maximum compression, apply techniques in this order:

1. **Prune first** -- Remove unnecessary weights (structured weight removal)
2. **Project second** -- Reduce layer dimensions (`compressNetworkUsingProjection`)
3. **Quantize last** -- Convert to lower precision (INT8)

### When to Include Projection

`compressNetworkUsingProjection` supports `convolution1dLayer`
(since R2024b), `convolution2dLayer`, `fullyConnectedLayer`, `lstmLayer`, and
`gruLayer`. Include projection when:

- The user's goal is **flash reduction** (projection shrinks weight matrices), AND
- The user can tolerate **retraining / fine-tuning** (highly recommended after projection), AND
- The model contains at least one supported layer type, AND
- No projectable layer shares learnable parameters via weight tying (unsupported).

**Skip projection when:**

- The user's goal is purely latency with no flash constraint
- The user's goal is SRAM reduction only (projection does not shrink activation memory)
- Retraining is not acceptable
- The model has no supported layer types

### Reporting Compression Results

After each compression step, summarize the outcome (accuracy delta vs. the
uncompressed baseline, flash/SRAM savings) so the user can make a go/no-go
decision before proceeding. No fixed template is required.

**Anti-pattern: do not hardcode numeric values in print statements.** Always
read the values from MATLAB variables computed in the same run. If a script is
re-executed with different inputs or a different model, hardcoded numbers in
`fprintf`/`disp` strings will silently lie about the new results.

```matlab
% BAD — value is baked into the format string:
fprintf("Quantization MAE: 1.2e-3 (within budget)\n");

% GOOD — value is computed and printed from a variable:
mae = mean(abs(yBase(:) - yQuant(:)));
verdict = "FAIL";
if mae < budget
    verdict = "PASS";
end
fprintf("Quantization MAE: %.3e (budget: %.1e) — %s\n", mae, budget, verdict);
```

## Compression Validation

After any compression step, always validate:

```matlab
% Compare original vs. compressed accuracy using testnet
lossOrig = testnet(net, XTest, TTest, "loss");
lossComp = testnet(compressedNet, XTest, TTest, "loss");
fprintf("Original loss:   %.4f\n", lossOrig);
fprintf("Compressed loss: %.4f\n", lossComp);
fprintf("Loss increase:   %.4f\n", lossComp - lossOrig);

% Model size comparison using analyzeNetwork (works for all compression types)
naOrig = analyzeNetwork(net, Plots='none');
naComp = analyzeNetwork(compressedNet, Plots='none');
fprintf("Original learnables:   %d\n", naOrig.TotalLearnables);
fprintf("Compressed learnables: %d\n", naComp.TotalLearnables);
fprintf("Reduction: %.1f%%\n", (1 - naComp.TotalLearnables/naOrig.TotalLearnables) * 100);
```

## CRITICAL Rules Summary

1. **prepareNetwork(quantObj) before calibrate()** -- `prepareNetwork` takes the
   `dlquantizer` object (not a `dlnetwork`) and mutates it in place. It handles
   unfused batch normalization, certain LSTM state configurations, and unpacks
   projected layers into their underlying built-in layers. Without it, calibration
   may fail with fi() type errors on networks that need fusion.

2. **Projected-layer codegen** -- `lstmProjectedLayer` and `gruProjectedLayer`
   are supported by `coder.loadDeepLearningNetwork` for generic C/C++ codegen
   (no MKL-DNN / ARM Compute acceleration). A `ProjectedLayer` wrapper is
   supported only when its contents are stateless (conv/FC, or LSTM/GRU in
   stateful-I/O mode). When in doubt, call `unpackProjectedLayers()` before
   saving for the direct MATLAB Coder path — that produces the most
   codegen-friendly form. **Not required for the Simulink path in R2026a:**
   `exportNetworkToSimulink` accepts projected networks directly.

3. **quantize() output is deployable via Simulink, NOT via direct MATLAB Coder** --
   `coder.loadDeepLearningNetwork` does not accept the output of `quantize()`. For
   embedded deployment of a quantized network, use `exportNetworkToSimulink(qNet)`
   followed by `slbuild`. For the direct MATLAB Coder path, use the uncompressed,
   pruned, or unpacked projected float32 network.

4. **Use ExecutionEnvironment="MATLAB"** -- For target-agnostic C/C++ code generation, always
   set `ExecutionEnvironment` to `"MATLAB"` when creating the dlquantizer.

5. **Compression Library is a support package** -- It is NOT detected by
   `detect_matlab_toolboxes`. Use `matlabshared.supportpkg.getInstalled` to check.

## Workflow Pattern 1 Compression Targets

For lean hardware deployment (Cortex-M):

| Metric             | Target                  | Notes                              |
|--------------------|-------------------------|------------------------------------|
| Model size         | < 500 KB (ideally < 100 KB) | Flash/ROM constraint          |
| RAM usage          | < 64 KB                 | SRAM constraint for inference      |
| Inference time     | < 10 ms (application-dependent) | Real-time constraint        |
| Data type          | int8 or fixed-point     | No FPU on some targets             |
| Accuracy drop      | < 2% relative           | Application-dependent tolerance    |
